security basics

A starting point if you are new to running a Linux server: how to watch resource use, how to stop logs from filling the disk, and how to tell normal traffic from an attack. Written for this server specifically — commands marked (tested) were run against the live journal during a debugging session.

1. Watch system load

uptime shows three numbers: the average number of processes waiting for CPU over the last 1, 5 and 15 minutes. They only mean something relative to how many CPU cores the server has.

uptime
# 14:32:01 up 12 days,  3:04,  1 user,  load average: 0.15, 0.22, 0.19

nproc
# 2

A load average of 1.8 on a 2-core machine means the CPUs are almost saturated. The same 1.8 on an 8-core machine is nothing to worry about. Always read load next to nproc.

For a live, per-process view (CPU%, memory%, who is using it):

top
# or, easier to read:
htop

Memory specifically:

free -h
#                total        used        free      shared  buff/cache   available
# Mem:           3.8Gi       1.2Gi       512Mi        45Mi        2.1Gi       2.3Gi

2. Watch container resource use

System-wide numbers do not tell you which container is the problem. docker stats does, live, per container:

docker stats
# NAME                                CPU %     MEM USAGE / LIMIT   MEM %
# bibleguessr-production-nginx-1      0.02%     8MiB / 3.8GiB       0.2%
# bibleguessr-production-bibleguessr-api-1   4.10%   180MiB / 3.8GiB   4.7%

Add --no-stream for a single snapshot instead of a live refresh (useful in scripts):

docker stats --no-stream

If one container's CPU% is pinned near 100% while uptime looks fine overall, the problem is in that one service, not the host.

3. Watch disk space

df -h /
# Filesystem      Size  Used Avail Use% Mounted on
# /dev/sda1        40G   14G   24G  37% /

Docker volumes and images accumulate over time (old image versions from task docker:site:pull, unused volumes). Find what is actually taking space:

docker system df
docker system df -v   # broken down per image/volume

4. Stop logs from filling the disk

This server's nginx container logs to journald (NGINX_LOGGING_DRIVER=journald in env/nginx.env), not to a file Docker rotates itself. journald has its own size cap — check it before it becomes a problem:

journalctl --disk-usage
# Archived and active journals take up 512.0M in the file system.

Set a hard ceiling in /etc/systemd/journald.conf:

sudo sed -i 's/^#SystemMaxUse=.*/SystemMaxUse=500M/' /etc/systemd/journald.conf
sudo systemctl restart systemd-journald

Or shrink what is already stored, without touching the config permanently:

sudo journalctl --vacuum-size=500M
sudo journalctl --vacuum-time=2weeks

If a service ever used the json-file driver instead (the default in docker-compose.yml when NGINX_LOGGING_DRIVER is unset), that log grows unbounded unless you cap it explicitly, since Docker does not rotate json-file logs on its own by default:

docker inspect --format='{{json .HostConfig.LogConfig}}' bibleguessr-production-nginx-1

5. Tell normal traffic from an attack

Find the exact container name first — Compose names containers <project>-<service>-<n>, and the project name here is bibleguessr-production (the name: at the top of docker-compose.yml):

docker ps --format '{{.Names}}'
# bibleguessr-production-nginx-1
# bibleguessr-production-bibleguessr-api-1
# bibleguessr-production-vaultwarden-1

Docker tags every journald entry with a CONTAINER_NAME field, so you can filter to just that container. (tested)

journalctl CONTAINER_NAME=bibleguessr-production-nginx-1 --since "1 hour ago"

No space around =. CONTAINER_NAME= bibleguessr-production-nginx-1 (with a space) is two separate, broken arguments and journalctl exits with an error.

-o cat strips journald's own timestamp/hostname fields, leaving just the nginx log line, so field-based tools like awk line up correctly. The first field of the realip log format (nginx/includes/log-formats.conf) is the client IP. (tested)

journalctl CONTAINER_NAME=bibleguessr-production-nginx-1 -o cat --since "1 hour ago" \
  | awk '{print $1}' | sort | uniq -c | sort -rn | head -20
#     612 103.196.9.108
#      12 85.191.83.141
#       9 34.67.84.58

A unique IP count (sort -u) does not tell you whether you are under attack — a busy hour of normal visitors easily produces 40+ distinct IPs, several of which are known cloud/CDN/relay ranges (e.g. 17.166.x is Apple Private Relay, 104.23.x is Cloudflare). What matters is concentration: one IP with hundreds of requests while everyone else has single digits, as in the example above.

Live instead of historical, filtered to just the IPs:

journalctl CONTAINER_NAME=bibleguessr-production-nginx-1 -o cat -f | awk '{print $1}'

Requests already flagged as suspicious use a separate log format (security_events, defined in nginx/includes/tarpit.conf) — a quick way to see only the traffic nginx itself considered abnormal:

journalctl CONTAINER_NAME=bibleguessr-production-nginx-1 -o cat --since "1 hour ago" | grep SECURITY_EVENT

These two lookups are wrapped as tasks in Taskfile.Security.yml:

task security:nginx           # raw log, last hour
task security:nginx:top-ips   # request count per IP, last hour, sorted

6. Block an attacker

Confirmed bad IPs go in the $bad_guys map in nginx/includes/bad-guys.conf, one per line, with the hit count as a comment so the next person knows why it is there:

203.0.113.5 1;  # 340 hits to /wp-admin in one hour

Requests from a listed IP get dropped with 444 (connection closed, no response) before any other processing — see nginx/includes/security-checks.conf. After editing the file, reload nginx without downtime:

docker exec bibleguessr-production-nginx-1 nginx -t && \
docker exec bibleguessr-production-nginx-1 nginx -s reload

This file is included directly (not a .conf.template), so no task docker:nginx:generate-conf step is needed — just nginx -t and reload.

7. Recommended CLI tools

ToolWhy
htopInteractive top: sortable, shows per-core load, easier to read than plain top
ncduInteractive du: find what is eating disk space without guessing paths
ssModern replacement for netstat; ss -ltnp shows what is listening on which port
jqParse JSON from the command line — useful for docker inspect output
lnavLog file navigator: understands timestamps, lets you jump/filter/search across large logs, including piped journald output
fail2banAutomates what section 6 does by hand: watches logs and bans IPs that match a pattern too often. Not currently installed on this server — evaluate before adding another moving part
sudo apt install htop ncdu iproute2 jq lnav

8. Recommended VS Code extensions

Since you connect over SSH, the most useful extension is the one that lets VS Code itself run on the server:

ExtensionWhy
Remote - SSH (ms-vscode-remote.remote-ssh)Open this repo directly on the server; edit, and run terminals, without a separate SSH client
Docker (ms-azuretools.vscode-docker)Browse running containers, tail logs and open a shell inside one from the sidebar
ShellCheck (timonwong.shellcheck)Lints the Bash scripts in lib-bash/ and scripts/ as you edit; catches quoting bugs before they run in production
YAML (redhat.vscode-yaml)Validation and autocomplete for the Taskfiles and docker-compose.yml
DotENV (mikestead.dotenv)Syntax highlighting for the files under env/, so a stray unquoted value stands out
