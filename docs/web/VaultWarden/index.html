Vaultwarden

Self-hosted Bitwarden server. Runs behind nginx on its own host name and is used with the regular Bitwarden clients.

Start and check

Vaultwarden starts with the rest of the stack. It publishes no ports and is reachable only through nginx.

task docker:site:up
curl https://vault.bibleguessr.srv/alive
# "2026-09-29T20:14:02.113Z"

Logs:

docker logs -f bibleguessr-production-vaultwarden-1

Configuration

Two files, created by scripts/env-init.sh:

FileVariableExample
env/nginx.envDOMAIN_VWvault.bibleguessr.srv
env/vaultwarden/vaultwarden.envDOMAINhttps://vault.bibleguessr.srv
SIGNUPS_ALLOWEDfalse
ADMIN_TOKEN'$argon2id$v=19$…' (empty = /admin disabled)

After changing the env file, the container must be recreated. docker restart does not reread the file.

task docker:site:up
docker inspect -f '{{range .Config.Env}}{{println .}}{{end}}' \
  bibleguessr-production-vaultwarden-1 | grep SIGNUPS
# SIGNUPS_ALLOWED=false

Admin panel

1. Hash a long, random password:

docker exec -it bibleguessr-production-vaultwarden-1 /vaultwarden hash
# ADMIN_TOKEN='$argon2id$v=19$m=65540,t=3,p=4$...'

2. Paste the whole line into env/vaultwarden/vaultwarden.env, keeping the single quotes, and run task docker:site:up.

3. Open https://vault.bibleguessr.srv/admin and log in with the password, not the hash.

Create users

An admin cannot set a user's password. The master password is always created in the client, because it is what encrypts the vault. Instead, you invite the email address and the user creates the account.

Example without SMTP:

  1. /admin → Users → Invite User → theodor@example.com
  2. Open https://vault.bibleguessr.srv → Create account with exactly theodor@example.com
  3. Choose a master password. The account is active even though SIGNUPS_ALLOWED=false.

The master password cannot be reset. If you forget it, the vault is lost.

Clients

Use the official Bitwarden clients (browser extension, desktop, mobile). Choose Self-hosted on the login screen:

Server URL: https://vault.bibleguessr.srv

Mobile works only against the production domain. The phone cannot resolve .srv and does not trust the dev certificate.

Testing

The routing test runs the nginx config against a mock. It covers the host name, HTTP→HTTPS, WebSocket, X-Forwarded-For, large attachments, the login rate limit, and that tokens are never logged.

task docker:nginx:test

Manually: edit an item in the web vault. If it updates immediately in the browser extension, live sync over WebSocket works.

Pitfalls

SymptomCause and fix
Registration not allowed or user already exists Signups are disabled. Invite the email via /admin, or temporarily set SIGNUPS_ALLOWED=true and recreate the container.
ADMIN_TOKEN is enabled but has an empty value Expected when ADMIN_TOKEN is empty. /admin is then disabled.
A change to the env file has no effect The container was not recreated, or settings were saved in the admin panel. Save there writes /data/config.json, which overrides env. Use Reset defaults.
Certificate error after task dev:host:bootstrap nginx is still serving the old certificates: docker exec bibleguessr-production-nginx-1 nginx -s reload
429 on login or /admin nginx rate limit (zone vault_login). Wait a moment.
